## 0. 结论速览（TL;DR）

1. **本目录只有推理端，没有训练代码**；训练契约（观测/动作/网络/频率）可从 [`rl_control.py`](pkg_soccer/rl_control.py) 100% 反推，**奖励函数和仿真动力学必须自己重建**。
2. **复赛是 2v2**：每队 2 只狗；场地 **10 m × 5.5 m**；门宽 **1.5 m**；死区 = 距边线 **0.8 m** 的条带（球门口除外）；两狗互顶 **8 s** 裁判介入；进球后 **15 s** 复位；上下半场各 **4 min**、中场 **1 min**；胜 3 平 1 负 0。
3. 现有权重的 `field_geometry = [10, 5.5, 9.17, 1.5, 0.8, 8]` 与规则**几乎逐项对应**：9.17 m 是门刚体间距，即门线在围挡内侧 0.415 m；0.8/8 正是死区宽和僵持秒数。
4. 推荐训练路线：**2D 运动学仿真 → 23 维单狗射门 → 29 维 1v1 → 41 维 2v2（队友 + 最近对手 + 次近对手，团队共享奖励）**，不需要 Isaac；PPO + 128×128 MLP，CPU 可训。**41 维已实现并跑通全链路，见 §18。**
5. 部署端已补齐"比赛"三块：**2v2 支持、进球/死球后的自动复位（match loop）、死区/出界判罚** —— 见 **§19**（2026-11-17）。

## 2. 复赛规则要点（只保留影响建模与策略的）

### 2.1 场地（规则第 1 页）

| 元素 | 规则值 | 对应代码/权重 |
|---|---|---|
| 场地 | 长 10 m × 宽 5.5 m，四周有**边界围挡** | `field_length=10`，`field_width=5.5`（攻防默认） |
| 球门 | 两侧各一门，门口沿端线，**门宽 1.5 m** | `goal_width=1.5`（攻防默认）；单狗默认 1.53 是实测值 |
| 门刚体间距 | 规则未给；权重 `field_geometry` 为 **9.17 m** | `goal_x=4.585`（=9.17/2） |
| 门线到围挡 | 由 9.17 推得 **0.415 m**（球门框架/网进深） | `field_end_margin=0.415` |
| 死区 | **距边线 0.8 m** 的条带；球进死区 → 裁判就近发球 | `referee_needed()` 里 `±0.8` 判定（2026-11-17 起见 §19） |
| 中线 | 场地中央白色实线（用于选边/半场） | — |
| 球员出发点 | **四角内侧 0.5 m** 的绿色标记（起始位置，趴） | 场心坐标 (±4.5, ±2.25) |
| 中央发球点 | 场地中心 | 场心 (0, 0)；场坐标 (5, 2.75) |
| 开球点 | 中央发球点旁 **0.5 m** | 未建模（现场以裁判为准） |
| 发球点阵列 | **共 9 处**，十字标记，横向间距 **2.5 m** | 代码 `[(x,y) for x in (-2.5,0,2.5) for y in (-1.25,0,1.25)]`，即场坐标 x=2.5/5/7.5，y=1.25/2.75/4.25 |

### 2.2 赛制与时间（规则第 2 页）

- 全场 **9 min**：上半场 **4 min** → 中场 **1 min 交换半场** → 下半场 **4 min**；得分累积。
- **进球后暂停计时 15 s**：裁判把球放回**被进球方的发球点**，双方把狗放回**球员出发点**；15 s 后由**被进球方开球**；每球 1 分。
- 每队每场有 **1 次** 1 min 延时准备机会（上、下半场共用一次），到时无论是否准备好都开始计时。
- 半场结束换边、换开球方 → **策略必须能左右两侧都踢**。

### 2.3 队伍与排名（第 2、3 页）

- **每队两条狗**（1 号、2 号），即 **2v2**；比赛电脑显示两个终端（左 1 号、右 2 号）。
- 小组单循环，**胜 3 / 平 1 / 负 0**；同分依次比净胜球、总进球。

### 2.4 裁判介入与复位（第 2 页）

| 情况 | 规则处理 |
|---|---|
| 球出界 / 死球（卡住、进死区） | 裁判进场，**就近发球**到最近发球点；狗**不复位**，原位继续 |
| 两狗互顶无法脱身 **持续 8 s** | 裁判介入，就近发球点发球；狗不复位 |
| 狗摔倒起不来 / 程序趴着不动 / 边界卡住 | 裁判**停止该狗代码**、标记"抱起"；队员搬回出发点；可场外调试（**比赛时间不暂停**）；准备好后 10 s 由裁判重启 |
| 恶意冲撞 | **赛前审核代码**，发现主动攻击逻辑取消资格 |
| 举办方原因（网络/动捕异常） | 暂停、复位、重新计时 |

### 2.5 其他要求（第 3 页）

- 启动命令统一为 **`./start.sh`**，比赛时电脑由裁判接管。
- 场边随时准备抱狗，放到"启动位置"后向裁判喊"红 1 / 红 2 准备"。
- 赛题未覆盖的情况由裁判临时判定。

> **对策略的直接含义**：这是一项比"谁先进球、谁少失误"的比赛。4 min 内进球数决定胜负；**把球踢出界、踢进死区、把球弄停导致僵持，都等于把球权交给对方**——训练奖励必须体现这一点。

### 3.2 必须现场复测的一项

权重里的 **9.17 m** 是两队门刚体间距；按 10 m 围挡反推，门线在围挡内侧 **0.415 m**（球门框架进深）。三者（9.17、4.585、0.415）自洽。

**动作**：到场地用卷尺测"门刚体原点 → 围挡"的距离。
- 若 ≈0.415 m → 现有默认参数直接可用，训练环境按此建。
- 若明显不同（例如 0.2 或 0.6）→ 改 `goal_x`/`field_end_margin`，并按新几何重训或至少重标定。

### 3.3 代码缺口（比赛能跑但不像完整比赛）

| 缺口 | 现状 | 训练/部署要补什么 |
|---|---|---|
| **2v2** | [`rl_control.py`](pkg_soccer/rl_control.py) 只支持**一个** opponent 槽位 | 每只狗取"最近敌狗"填 `opponent`；队伍内不通信 |
| **进球后复位** | 进球即 `GOAL` 终态，节点不再启动 | ✅ 已实现（§19）：进球 → `WAIT_PLAY` 暂停 → 球回到任一发球点并静止 → `rearm()` 自动继续 |
| **死球/出界** | 规则模式 `stop()` 锁死；仅攻防 RL 有 `referee_wait` | ✅ 已实现（§19）：所有"死球事件 → 就近发球点 → 自动继续"统一走 `pause_play()/rearm()` |
| **开球权** | 无 | manager 记录"被进球方开球" |
| **15 s 暂停** | 无 | manager 计时，期间不发运动指令（发 END 帧） |
| **半场 4 min** | `max_run_time=120 s` | manager 按 4 min 计时；策略按事件复位 |
| **恶意冲撞** | 无惩罚 | 训练加碰撞惩罚 + 部署不加主动冲撞逻辑 |

## 4. 训练目标分解（三条路线，选第一条）

| 阶段 | 训练什么 | 观测 | 对手 | 产出 |
|---|---|---|---|---|
| **P1** | 单狗射门 + 追滚动球 | 23 维 | 无 | `policy_stage2_actor.npz` 替换版 |
| **P2** | 1v1 攻防（含裁判/死区处理） | 29 维 | 规则控制器 → 自博弈 | `policy_duel_attacker/defender` 替换版 |
| **P3** | 2v2（每队 2 只，最近敌狗） | 29 维（不改维度） | 2v2 自博弈 | 同一套权重 + 角色策略 |

**决策：不要改观测维度**。理由：

- 部署端 [`rl_control.py:127-172`](pkg_soccer/rl_control.py#L127-L172) 的 23/29 维布局、`Actor` 的层形状校验（[`rl_control.py:26-44`](pkg_soccer/rl_control.py#L26-L44)）都写死了 23/29；
- 2v2 只是把"最近敌狗"塞进唯一 opponent 槽（与 1v1 训练时"唯一对手=最近对手"分布接近）；
- 引入队友观测会变成 35 维，必须同时改推理端和导出，收益不如"角色分工"大。

**2v2 的工程实现**（不改策略维度）：

- 每队两只狗各跑一个 `soccer` 节点，分别用 attacker / defender 权重；
- 角色分工：attacker 抢球进攻；defender 站球门侧、只解围不冒进（可用简单的"球位启发式"切角色）；
- 每只狗的 `opponent_pose_topic` 指向**最近的敌狗**（由 manager 计算后切换话题或直接改配置）。

## 5. 仿真环境规格（照抄即可）

建议纯 numpy + gymnasium，20 Hz，单幕 = 一次"死球周期"，评估时跑满 4 min 半场。

### 5.1 坐标系与状态

```
世界系 Z-up，场地中心为原点，进攻方向 +X（与训练约定一致）
field: x ∈ [-5, +5], y ∈ [-2.75, +2.75]
门线: x = ±4.585, 门宽 1.5 → |y| ≤ 0.75
死区: |y| > 1.95 或 (|x| > 4.2 且 |y| > 0.75)
状态: dog(x,y,yaw,vx_world,vy_world,wz)、ball(x,y,vx,vy)、[opponent 同 dog]
```

### 5.2 狗动力学（一阶响应 + 延迟 + 打滑）

```python
# 动作 → 机身速度
cmd_body = clip(a, -1, 1) * [0.45, 0.20, 0.70]
sp = norm(cmd_body[:2])
if sp > speed_limit: cmd_body[:2] *= speed_limit / sp      # speed_limit 默认 0.30

# 指令延迟 1~4 帧（50~200 ms）
cmd = cmd_queue[-latency]

# 一阶惯性
v_body += dt * (cmd_body[:2] - v_body) / tau                # tau ∈ [0.08, 0.25]
w      += dt * (cmd_body[2]  - w) / tau_w                   # tau_w ∈ [0.10, 0.30]
# 打滑：v_body[1] += bias_y（±0.05）
# 噪声：v_body += N(0, 0.02)

yaw += dt * w
x += dt * (cos(yaw)*v_body[0] - sin(yaw)*v_body[1])
y += dt * (sin(yaw)*v_body[0] + cos(yaw)*v_body[1])
```

### 5.3 球

```python
# 滚动摩擦（拟合值 0.3~1.2 m/s^2）
v_ball *= max(0, 1 - decel*dt/norm(v_ball))
x_ball += dt * v_ball
# 与狗碰撞：接触半径 = r_ball(0.12) + r_dog(≈0.18) ≈ 0.30
#   法向恢复系数 e ∈ [0.3, 0.7]，切向传递 + 狗速分量
# 球速上限 12 m/s（与 Track 一致）
```

### 5.4 触球标志（必须与部署一致）

```python
# 部署用 Track 估计距离，阈值 0.43；训练里用同一套 Track 估计
contact_seen |= (dist(ball, dog) < 0.43)      # 一旦触发本幕保持
```

### 5.5 判定（与 `rl_control.py` 完全一致）

| 事件 | 条件 | 结果 |
|---|---|---|
| 进球 | 球心越过门线（`before < r ≤ after`）且 `|side| ≤ 门宽/2 − r` | +1 分，本幕结束 |
| 球出界 | 球心出 `|x|>5` 或 `|y|>2.75` | 本幕结束，就近发球点复位 |
| 死球 | 进死区；或球速 < 0.05 且 3 s 无人接近（可按规则"卡住"理解） | 本幕结束，就近发球点复位 |
| 僵持 | 两狗距离 < 0.56 且双方速度 < 0.08 持续 8 s | 本幕结束，就近发球点复位（狗不复位） |
| 超时 | 单幕 > 30 s（训练）/ 半场 4 min（评估） | 结束 |

### 5.6 复位流程（对齐规则第 2 页）

```
训练幕结束后：
  进球      → 球放【被进球方半场】3 个发球点中随机一处；双方回各自出发点；被进球方开球
  出界/死区  → 球放【最近发球点】；狗不复位（规则如此，但训练可随机决定是否复位）
  僵持      → 同上
  开场      → 球放中央发球点；双方在出发点（趴→起立后开始计时）
```

## 6. 奖励设计（对齐胜负目标）

用势函数整形（potential-based）避免 reward hacking：

```python
# 每步（dt=0.05）
Phi = 1.5 * dist(ball, 对方门) + 0.8 * dist(dog, 球后点)      # 越小越好
r  = gamma * Phi(s') - Phi(s)                                 # 平滑整形
r += 6.0 * (dist(ball,门)_prev - dist(ball,门)_now)            # 推进
r += 0.3 * cos(heading_err) * in_corridor                      # 对准
r += 1.0  首次触球
r -= 0.005                                                     # 时间成本（4 min 要效率）

# 终局
进球：+10（2v2 时全队共享）
被进球：-10
球出界 / 进死区：-3        # 等于把球权交给对手
僵持超 8 s：-3
碰撞对方狗：-2             # 规则禁止恶意冲撞
动作变化：-0.01 * ||Δa||²  # 平滑，防抖
```

**注意**：不要只奖励"球朝门推进"（会学会把球顶到自己半场边线再回推）；进球奖励必须包含"整球越线"判定；也不要用"射门次数"作奖励（会乱踢）。

## 7. 训练配置（PPO）

```python
SCALE = np.array([0.45, 0.20, 0.70], np.float32)

class TanhPolicy(ActorCriticPolicy):
    """与部署端同构：tanh 输出 + 挤压高斯。"""
    def _build(self, lr_schedule):
        super()._build(lr_schedule)
        self.action_dist = SquashedDiagGaussianDistribution(3)
    def _predict(self, obs, deterministic=False):
        f = self.extract_features(obs)
        return self.action_net(self.mlp_extractor.forward_actor(f)).tanh()

model = PPO(TanhPolicy, SubprocVecEnv([make_env] * 16),
            n_steps=512, batch_size=2048, learning_rate=3e-4,
            gamma=0.995, gae_lambda=0.95, clip_range=0.2,
            ent_coef=0.005, vf_coef=0.5, max_grad_norm=0.5,
            policy_kwargs=dict(net_arch=[128, 128], activation_fn=nn.Tanh,
                               log_std_init=-0.5))
model.learn(total_timesteps=5_000_000)   # 单狗；攻防 1e7 量级
```

### 7.1 课程（按比赛流程）

| 阶段 | 内容 | 步数 | 验收 |
|---|---|---|---|
| C0 | 固定球、空场，从出发点出发 | 0.5-1M | 95% 进球，平均 < 10 s |
| C1 | 随机球位 + 球随机滚动 | 1-2M | 90% 进球，25 s 内 |
| C2 | 加死区/出界判定 + 就近发球复位 | +1M | 死球率 < 10% |
| C3 | 1v1 对规则控制器（29 维） | 3-5M | 对基线胜率 > 50% |
| C4 | 1v1 自博弈（镜像、随机开球） | 5-10M | 净胜 > 0 |
| C5 | 2v2（每队 2 只，最近敌狗，共享奖励） | 5-10M | 团队胜率 > 50% |
| C6 | 域随机化加强 + 15 s 复位事件 | +2M | 影子模式无异常 |

### 7.2 自博弈要点

- 对手池：规则控制器（起步）→ 历史权重快照（每 200k 步存一版，随机抽取）；

- 每次 episode 随机：开球方、半场方向、球在哪个发球点、15 s 复位后的初始状态。

## 14. 单腿踢球（位控姿态）实现与标定

> **2026-11-17 起 `soccer.py` 已移除这条路径**（见 §19.6）：比赛节点只做"提速推球"。
> 本节内容只对独立脚本 `kick_action.py` / `kick_test.py` 有效，留作标定参考。

### 14.1 为什么用「位控姿态」而不是直接控关节

- CyberDog 2 的**关节级**控制在底层 LCM 接口 `motor_ctrl`（`cyberdog_motor_sdk`），需要开发者权限、网线/路由配置，且要求 500 Hz 级别的实时性；本包已经在 ROS 2 上跑，走底层会把部署复杂度放大一个量级。
- 官方**高层接口**里的「位控姿态」正好能单独抬一条腿：`motion_id` + `contact`（抬哪条腿）+ `foot_pose`（足端偏移）+ `duration`。
  出处：官方《运动控制二次开发接口》<https://github.com/MiRoboticsLab/blogs/blob/rolling/docs/cn/cyberdog_loco_cn.md>
  与 `motion_id_map.toml` <https://github.com/MiRoboticsLab/motion/blob/rolling/motion_action/preset/motion_id_map.toml>。

### 14.2 命令字段（官方文档确认）

| 字段 | 含义 | 本实现取值 |
|---|---|---|
| `motion_id` | 运控姿态 ID。`212` 位控姿态-相对姿态（官方 contact/foot_pose 的说明就在 mode/gait 21/0 下）；`211` 绝对姿态（**pos_des.z 必须给机身高度 0.1~0.32 m，给 0 会执行超时 3028**）；`213` 相对姿态-抬腿低刚度（握手用） | 默认 `212`，可切 211/213 |
| `duration` | 该命令块持续时间（ms），**位控必须 > 0**，间接控制到位速度 | 每步 120~500 ms |
| `contact` | 低 4 位：1=支撑、0=抬起；顺序 FR/FL/RR/RL；默认 `0x0F` | 抬右前 `0b1110`、左前 `0b1101`、右后 `0b1011`、左后 `0b0111` |
| `foot_pose[0:3]` | 抬起那条腿的足端坐标偏移（机身系：x 前、y 左、z 上，米）；后 3 位官方预留给视觉行走 | 后收 `x=-0.05`、抬腿 `z=0.12`、前摆 `x=+0.16, z=0.10` |
| `pos_des` | 质心位置偏移（米）；相对姿态下 z=0 表示不改高度 | 向支撑侧移 0.03 m |
| `rpy_des` | 机身姿态（弧度） | 0（可配 body_pitch） |
| `cmd_source` | 命令来源 | `0`=APP（默认；4=ALGO 可选） |

> 注意：ROS 侧数组字段默认是空数组、`contact` 默认 0；**留空/给 0 可能被解释成"四腿都抬起"**，所以 `leg_kick.build_request()` 把 14 个字段全部显式赋值。

### 14.3 动作序列（`pkg_soccer/leg_kick.py`）

```
进入 KICK → SERVO_END 停步态 → (600ms 过渡)
  enter   400ms  切到位控姿态：四腿支撑，足端/质心不动
  preload 250ms  屈膝收腿：foot=(后收 -0.06, 侧向 0, 高 0.10)
  extend  100ms  小腿前伸击球：foot=(前伸 +0.18, 0, 0.10)
  retract 200ms  收腿：foot=(后收 -0.036, 0, 0.08)
  recover 300ms  四腿支撑，足端归零
→ 下次控制周期恢复行走
```

- 总时长约 **1.85 s**（含 600 ms 过渡；可用 `kick_phase_scale` 统一缩放）；最后一步等满整段时长再恢复行走，避免腿没收完就切步态。
- **默认身体不动**：`kick_body_shift=0`，所有命令的 `pos_des=(0,0,0)`、`rpy_des=0`，只有被抬起那条腿的足端在动（相当于"站住、小腿伸出踢球"）。需要重心转移时才把 `kick_body_shift` 设 >0，此时序列会插入 `windup` 步骤。
- `enter` 是"切位控"步骤：真机上第一条位控命令如果直接是抬腿，运控还在从步态/站立切换，容易 3028 超时。
- 控制器进入 `KICK` 时触发；踢球期间**不发布行走速度**（先 `SERVO_END`），序列完成后控制器自然进入 `ASSESS`。
- 失败处理：服务超时/被拒 → `controller.stop()` 锁停 + 自动补发一条"四腿支撑归零"；节点退出时也会补发恢复命令。

### 14.5 台架标定流程（务必按顺序）

0. **先下充电桩**：`motion_status.switch_status=14` 是 CHARGING，运动接口会受限；确认变成 `0`（Done）再试；
1. **软垫/悬空**：让狗能自由抬腿，人在旁边随时扶住；
2. `dry_run:=true`：看日志里的时序与 `contact` 掩码是否正确（`0b1110` 只抬一条腿）；
3. `dry_run:=false` + `kick_phase_scale:=1.5`：看慢动作，确认只抬目标腿、不抖、不碰地；
4. 放一个球在狗右前方（`kick_leg:=fr`），逐步微调 `kick_forward_reach` / `kick_strike_height` / `kick_distance`；
5. 场地低速试（`enable_motion:=true`，先 `kick_mode:=leg` + 手动足球摆位），再进比赛流程。

### 14.7 失败排查

| 现象 | 排查 |
|---|---|
| 服务超时 | `ros2 service list | grep motion_result_cmd`；确认 `dog_name` 与命名空间 |
| `result=false`、`code=3xx` | 运控状态不允许切换：先确认已站稳（112）、`switch_status=0`；必要时先发 111 |
| 腿完全不动 | 桥接可能不接受空数组/ contact=0；本实现已全字段赋值。仍不动时试 `kick_motion_id:=212/213` |
| 抬错腿 | `contact` 位序是 FR/FL/RR/RL；`0b1110`=右前 |
| 动作太慢/太抖 | `kick_phase_scale` 调速度；`kick_body_shift` 加大帮助卸载；减小 `kick_lift_height` |
| 踢不到球 | 增大 `kick_forward_reach`；把 `kick_distance` 调到 0.45；确认狗头朝向与球门一致 |

### 14.8 已知限制

1. **未在真机验证**：`foot_pose` 的坐标符号/可达范围、位控刚度都受运控内部限制，必须按 14.5 台架标定；
2. 位控姿态对地面摩擦、负载、电池电压敏感，踢球成功率需要现场统计；
3. 单腿踢比推球慢（约 1.1 s/次），比赛中建议**先保留 push 作为兜底**，leg 作为加分项；
4. 若踢球瞬间球被人/狗碰到，序列不会中断（腿会按计划收回），这是有意的安全设计。

## 15. 真机首测记录与修正（2026-11-15）

### 15.1 现场日志

```
状态：motion_id=0 switch=14 progress=100 ori_err=0 foot_err=0     ← switch=14 是 CHARGING
站立请求：result=True code=0
windup: result=False code=3028 (742ms)  当前 motion_id=214 switch=0 progress=10
```

### 15.2 原因分析

| 线索 | 结论 |
|---|---|
| `switch_status=14` | **CHARGING（充电中）**。运控在充电状态下会限制运动模式切换，脚本应先拒绝执行而不是硬发命令 |
| `motion_id=214`、`progress=10` | 机器人已切到位姿插值（pose interpolation）状态但只到 10%，说明模式切换尚未完成/被卡住 |
| `code=3028` | 官方 `MotionManagerCodeDescribe_`：**动作执行超时**（不是参数错误） |
| `motion_id=211`（原默认） | 211 是**绝对姿态**，要求 `pos_des.z` 给出机身高度（0.1~0.32 m），我们给的是 0 → 目标姿态不可达 → 执行超时 |
| 站立后仅 1 s 就发位控 | 111 站立切换本身需要时间，位控命令赶在切换中途，进一步放大超时风险 |

### 15.3 已做的修正

1. **默认 `motion_id` 改为 212**（相对姿态，官方 contact/foot_pose 的说明就在 21/0 下）；211 仅在显式指定时使用，并自动把 `pos_des.z` 设为 `body_height`（默认 0.22 m）；
2. **新增 `enter` 步骤**（500 ms）：先发一条"四腿支撑、足端/质心不动"的位控命令，让运控完成步态→位控切换，再抬腿；
3. **过渡时间 250 → 600 ms**；
4. **站立判定加严**：要求 `switch_status=0` 且 `motion_id=112`（或 111 进度≥96），并再等 `stand_settle=2 s`；
5. **充电保护**：检测到 `switch_status=14` 直接报错退出（`--allow-charging` 可强制）；
6. **`cmd_source` 默认改为 0（APP）**，并提供 `--cmd-source`；
7. **错误码翻译**：3003/3008/3010/3011/3013/3028/3029/3040/3041 直接打印中文含义。

### 15.4 下一次真机测试步骤

```bash
# 0) 把狗从充电桩上取下，确认状态
ros2 topic echo /<dog_name>/motion_status --once   # 期望 switch_status=0, motion_id=112

# 1) 只打印新序列（应有 enter 步骤）
python3 kick_action.py --leg fr

# 2) 真机慢速
python3 kick_action.py --leg fr --execute --scale 1.5

# 3) 若仍有异常：先试 213（低刚度抬腿）确认"能抬腿"
python3 kick_action.py --leg fr --execute --motion-id 213 --scale 1.5
```

### 15.5 第二轮修改：身体不动的"伸小腿"踢法

需求变化：**让身体尽量不动，只把一条腿的小腿伸出去踢球**。

改动：

1. 默认 `kick_body_shift = 0`：所有命令的 `pos_des=(0,0,0)`、`rpy_des=0`，机身姿态与质心全程不动；
2. 删除固定的 `windup` 移重心步骤（只有 `kick_body_shift>0` 时才插入）；
3. 把动作改成"**屈膝收腿 → 伸小腿 ↔ 击球 → 收腿**"：
   - `preload` 250 ms：足端后收 -0.06 m、抬高 0.10 m（膝盖弯曲）；
   - `extend` 100 ms：足端前伸 +0.18 m、高度 0.10 m（小腿伸出，快速击球）；
   - `retract` 200 ms：足端回收、抬高；
   - `recover` 300 ms：四腿支撑、足端归零；
4. 总时长约 1.85 s（含 600 ms 切位控过渡）。

真机风险：身体完全不动时，抬起一条腿会让支撑三角变小，可能触发运控的平衡策略（身体自己让一点）或 `footpos_error`。如果发现抬腿瞬间身体被"顶"一下或报足端越界，按顺序试：

1. `--shift 0.02`（只加一点点重心转移，仍然几乎看不出来）；
2. 减小 `--reach`（0.18 → 0.14），减小 `--lift`（0.10 → 0.08）；
3. 用 `--motion-id 213`（低刚度抬腿）先确认单腿动作能成立，再换回 212。

## 16. 用快走（305）的摆动腿踢球

> **2026-11-17 起 `soccer.py` 已移除这条路径**（见 §19.6）：比赛节点只做"提速推球"。
> 本节内容只对独立脚本 `gait_kick_action.py` 有效，留作参考。

### 16.1 可行性结论

**可以，但它是"走中踢"，不是定点踢。**

- 305 是快速对角小跑：摆动腿在腾空相向前摆，足端相对机身的前向速度约 0.5~1.0 m/s，再叠加机身速度；
- 抬腿高度 `step_height` 可到 0.05~0.08 m，球心约 0.12 m，足端会扫到球的下半部，把"身体推球"变成"腿扫球"；
- 优点：**全程走 305，不需要切位控**（避开真机 3028 那一类问题），实现简单、鲁棒；
- 缺点：机身会随球前进 0.2~0.4 m，出球方向精度不如单腿位控，适合"向前踢/解围"，不适合精细角度射门。

### 16.2 做法

1. 订阅 `motion_status`，用 `contact` 低 4 位（1=触地、0=抬起，位序 FR/FL/RR/RL）判断目标腿是否刚离地（1→0）；
2. 检测到离地瞬间，发一段**短促脉冲**：
   - `vel_des=[burst_speed, 0, wz]`（默认 0.75 m/s）
   - `step_height=[0.06, 0.05]`（前腿抬高，让足端去扫球）
   - 持续 `burst_ms`（默认 200 ms）
3. 脉冲结束立即回落到正常 `step_height=0.05`，避免整段一直在推球；
4. 如果 `contact` 一直不变化（某些固件不更新），`--sync-leg off` 用固定时序踢。

### 16.3 单独测试 `gait_kick_action.py`（单文件，推荐先做）


参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `--speed` | 0.75 | 脉冲前进速度 m/s |
| `--burst-ms` | 200 | 脉冲时长 |
| `--step-front/back` | 0.06/0.05 | 脉冲时前后抬腿高度（上限 0.08） |
| `--sync-leg` | `fr` | 用哪条腿的离地相位触发；`off`=不检测 |
| `--warmup-ms/speed` | 250 / 0.15 | 先低速走一小段进入 305 |
| `--phase-timeout-ms` | 350 | 等不到相位时的兜底 |

## 17. 全力推球（push 模式：1.5 m/s × 450 ms）

### 17.1 需求与实现

需求：踢球时**直接加到最大速度、腿不做动作，直接把球推出去**；并平衡"狗冲刺距离"和"球的速度"。

实现（`kick_mode:=push`，默认）：

- 控制器进入 `KICK` 时，节点锁定当前前进方向；
- 直接以 `kick_max_speed`（默认 **1.5 m/s**，协议 `vel_des` 前进上限）发布 `MotionServoCmd`；
- 持续 `kick_max_ms`（默认 **450 ms**，见 §17.5 分析），`step_height` 保持 `walk_step_height`（0.05），**不抬腿、不切位控**；
- 到时回到控制器速度；若提前进球/终止则立即停止。

### 17.2 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `kick_mode` | `push` | push=全力推球 / leg=位控单腿 / gait=305 摆动腿 |
| `kick_max_speed` | `1.5` | 脉冲速度，m/s，范围 [0.1, 1.5]（协议上限） |
| `kick_max_ms` | **450** | 脉冲时长，范围 [50, 2000] |
| `walk_step_height` | `0.05` | 推球时步高（保持默认，不抬腿） |
| `kick_distance` | `0.38`（Config） | 触发距离；推球建议 0.45，给加速留空间 |

### 17.3 启动命令

```bash
ros2 run pkg_soccer soccer --ros-args -p enable_motion:=true \
  -p kick_mode:=push \
  -p kick_max_speed:=1.5 -p kick_max_ms:=450 \
  -p kick_distance:=0.45
```

### 17.4 单独测试

`gait_kick_action.py` 的 `--push` 预设与比赛节点完全等价（1.5 m/s × 450 ms、不检测相位、步高 0.05）：

```bash
python3 gait_kick_action.py --push                 # dry-run 看计划
python3 gait_kick_action.py --push --execute       # 真机：走 250ms 后全力推 450ms
python3 gait_kick_action.py --push --execute --speed 0.8 --burst-ms 300   # 先低速
```

### 17.5 冲刺距离 vs 球速：450 ms 是怎么来的

假设：切入速度 0.55 m/s、305 步态加速时间常数约 0.15 s、加速后约 0.15 s 碰到球、推球期间球速≈机身速度（持续接触）、球出脚后滚动减速度 0.4~0.8 m/s²（取 0.6 估算）：

| 脉冲时长 τ | 狗冲刺距离 1.5·τ | 球离脚速度（估计） | 球离脚后滚动距离 | 球总推进（推+滚） |
|---|---|---|---|---|
| 0.20 s | 0.30 m | ≈0.8 m/s | ≈0.53 m | ≈0.83 m |
| 0.30 s | 0.45 m | ≈1.15 m/s | ≈1.10 m | ≈1.55 m |
| 0.40 s | 0.60 m | ≈1.32 m/s | ≈1.45 m | ≈2.05 m |
| **0.45 s** | **0.68 m** | **≈1.38 m/s** | **≈1.59 m** | **≈2.27 m** |
| 0.50 s | 0.75 m | ≈1.41 m/s | ≈1.66 m | ≈2.41 m |
| 0.60 s | 0.90 m | ≈1.45 m/s | ≈1.75 m | ≈2.65 m |
| 0.80 s | 1.20 m | ≈1.48 m/s | ≈1.83 m | ≈3.03 m |

结论：

1. **球速在 0.4~0.5 s 就基本饱和**（达到 1.5 m/s 的 88%~94%），再往后延长时间只增加狗的冲刺距离（每多 100 ms 多冲 0.15 m），球速提升 <5%；
2. **450 ms 是折中点**：狗只冲 0.68 m（从触发点算还留在半场内，不冲过头），球以约 1.4 m/s 出脚、总推进约 2.2~2.5 m；
3. 如果目标距离超过 2.5~3 m，push 模式（球速上限 1.5 m/s）本身不够——要么分两次推、要么换 `gait`（利用摆动腿脚速 > 机身速度）或 `leg` 位控踢；
4. 如果真机打滑导致 305 加速慢，球速曲线整体右移：**用 `record_motion` 录一段**，看 `cmd_vx` 到 1.5 的时刻和球速峰值，把 `kick_max_ms` 定在"球速达到峰值 + 100 ms"即可，通常落在 **400~550 ms**。

### 17.6 注意

1. **1.5 m/s 是协议 `vel_des` 的文档上限**（整机标称最大前进 1.6 m/s），固件可能再限幅；实际速度用动捕/`record_motion` 核实。
2. 450 ms × 1.5 m/s ≈ 0.68 m 位移，加上触发距离，球会被推出 1~2 m——**注意前方人员、门柱和边界**。
3. 速度越高冲击和打滑越大；第一次建议 `kick_max_speed:=0.8`、`kick_max_ms:=300`，确认无误再上 1.5/450。
4. 方向取控制器进入 KICK 时的 `drive_to` 方向，脉冲期间不再修正，**对准后再触发**。
5. 与 `leg`/`gait` 模式互斥：`kick_mode` 一次只能选一个。

## 18. 2v2 正式扩展：41 维观测（队友 + 双对手）与训练流程（2026-11-16 更新）

### 18.1 为什么必须加维度

§13 的做法是"2v2 但只看最近的一只敌狗"（29 维）：能上场，但策略**看不见队友**，
两只狗会同时压球、抢同一个位置。裁判规则里 2v2 是每队 2 只狗，协作只能来自
"看得见队友"，所以观测必须显式给出队友与第二只对手。

做法：**在 29 维后面追加两个 6 维块**，前 29 维逐位不变。好处是

1. 旧的 29 维权重仍然能加载、能跑，不被破坏；
2. 41 维训练的初始权重可以直接用旧 29 维第一层"前 29 列照抄 + 新增列置 0"热启动，
   初始行为与旧策略完全等价（见 §18.6 第 1 步）；
3. 训练/部署只需同步一处公式，`python -m train.verify --contract` 会逐位对比。

### 18.3 槽位约定（训练与部署必须一致）

1. **对手按距离升序**：`23-28` 放最近的合法对手，`35-40` 放第二近的。
   排序用狗到对手的欧氏距离，输入是同一帧的 `Track` 位置（带噪声），两侧同源。
2. **最近对手是硬要求**：没有它就 `WAIT_POSE`，不输出运动指令（与 1v1 行为一致）。
3. **队友与次近对手可缺**：未配置话题、断流、轨迹不连续 → 该 6 维**整块填 0**。
   合法朝向必满足 `sin²+cos²=1`，所以 `(0,0)` 能被策略识别为"看不到这个刚体"。
4. **训练端模拟断流**：`EnvConfig.body_dropout`（默认 0.05，粘滞约 0.3 s）随机把
   这两个槽位填 0，逼策略在"队友看不见"时也不慌。
5. 年龄槽 `20-22` 仍然只统计狗/球/最近对手，保持前 29 维语义不变。

### 18.8 风险与已知限制

1. **维度锁定**：41 维权重必须配 41 维观测；把 29 维权重喂给 41 维环境会直接报错
   （`Actor` 校验 obs_dim，`peer.py` 也会拦），不要试图"混用"。
2. **对手排序在等距时会抖动**：两只对手离狗几乎一样近时，`23-28` 与 `35-40`
   会互换。训练分布里同样存在，策略能容忍，但不会做"身份跟踪"。
3. **脚本队友较弱**：单只脚本狗贴球后容易原地打转，只适合当第一轮
   的陪练；跑完第 1 轮就应切 `--peer` 用权重当队友/对手。
4. **没有 15 s 暂停**：进球后环境立即复位，实际比赛的暂停/复位仍需场边流程。
5. **观测仍无归一化**：不要加 `VecNormalize`，部署端没有统计量。

### 18.9 观测"性价比"：速度方向值不值这 2 维（2026-11-16 实测）

先说结论：**每个刚体的 6 维块里已经含 2 维相对速度 `(vx, vy)`，它就是"方向×大小"**，
所以"加入对手速度方向"这件事本身不额外花维度；不要再单独拆一个"方向单位向量"出来。

三条依据（都可复现，见 `train/README.md` §11）：

1. **成本侧可忽略**：网络首层 128×41 → 加 2 维只多 256 个参数（占全部 2.2 万参数的 1.2%）；
   20 Hz 下单次推理 MACs 从 5.2k 到 5.5k。真机侧额外开销为 0——`Track` 本来就在
   给每只刚体算速度，动捕话题数不变。
2. **方向本身在低速时不可靠**：`Track` 0.1 s 回归在 0.008 m 噪声下，速度误差 ≈0.10 m/s；
   方向误差 5°@0.5 m/s、**13°@0.3 m/s、30°@0.15 m/s**。所以"只给方向"比"给速度矢量"
   更容易误导；保留幅值让网络自己决定信多少，才是最省的编码。
3. **行为消融**（40 万步热启动微调，3 种子 × 2 半场）：
   - 训练有速度、推理把三只刚体速度全遮掉：进球 5.00 → 4.67（噪声级）、球推进 2.33 → 2.37 m。
     **对"抢球→推射"这个技能，对手速度方向的边际收益 ≈ 0**；
   - 但训练期就遮掉速度/朝向会直接崩（球推进 -0.85 / -1.66 m，前者失球 0.67）——
     说明热启动的 29 维旧权重本身依赖这几位（敏感度：对手速度 3.5%、朝向 4.9%，
     都高于其位置的 0.9%）。**所以这 2 维不能砍**，砍了要用几倍算力重学；
   - 真正值钱的是**队友块**：遮掉后贴球率反而升到 77%（抢球更凶），但球推进 0.36 m、
     进球 1.67 → "两只狗挤同一个球"的典型症状。

花钱优先级（同样 2~6 维预算）：

| 选项 | 维度成本 | 收益 | 建议 |
|---|---|---|---|
| 队友 6 维 | 已加 | 遮掉后 5.00 → 1.67 球/场 | 最高优先，别省 |
| 最近对手 0.5 s 预测位置 | +2（只在最近对手上） | 未测，理论上限≈速度方向那点差距 | 下一步可选 |
| 速度方向单位向量 + 速率 | +1（3 替代 2） | 信息等价、更贵 | 不加 |
| 三只狗都加预测位置 | +6 | 不随数量线性 | 不划算 |

另外一条比"多加 2 维"重要一个数量级的坑：**从零训练 40 万步会塌缩成饱和常量**
（贴球率 0.000、球推进 -0.11 m、`vy` 饱和 0.70 一路退到角落；把死球惩罚从 -3 改成 0
只把贴球率抬到 0.019，主因是探索不足 + tanh 饱和）。必须 `--init` 用 29 维旧权重热启动。

### 18.10 奖励改造实测：推进 / 团队控球 / 无球干扰（2026-11-16）

需求：① 球在己方半场扣分（鼓励进攻）② 同队两狗持球时等价（鼓励协作）
③ 非持球狗干扰对方持球狗 ④ 短程传球是否可行。

②其实早就成立：`_reward` 全部按**队**结算，同队两只狗拿到的数完全相同
（`reward[i] = team_reward[TEAM_OF[i]]`），不存在"谁碰球谁多拿"。
①③已实现为可开关的三项（`--reward-half / --reward-possess / --reward-press`），
但**默认关闭**——因为实测它们在这套预算下都是负收益。

同一套 29 维热启动权重、同样 30 万步、3 种子 × 2 个 4 min 半场：

| 奖励配置 | 球推进 | 控球率 | 进球/场 | 失球/场 | 死球/场 |
|---|---|---|---|---|---|
| **旧奖励（基线）** | **2.33 m** | 50.1% | **5.00** | 0.00 | 9.3 |
| 只加推进 0.4 | −0.85 m | 42.9% | 0.67 | 0.17 | 4.8 |
| 推进 0.4 + 控球 0.01 | −0.80 m | 70.4% | 0.83 | 0.67 | 11.0 |
| 三项全开 0.4/0.01/0.01 | 0.32 m | 63.0% | 0.00 | 0.00 | 12.7 |
| 三项调低 0.15/0.002/0.003 | 1.97 m | 62.0% | 2.17 | 0.17 | 12.7 |
| 三项半场门控 0.15/0.004/0.004 | 1.63 m | 57.2% | 2.67 | 0.00 | 11.0 |

诊断：

1. **量级失衡**：0.01/步 × 600 步（30 s 一幕）= 6 分，控球+干扰合计 12 分 > 进球 10 分。
   策略于是选择"抱着球盘带 + 贴着对手"，控球率涨到 70%，但球被带向**自家**半场
   （推进 −0.80 m），进球反而归零。这就是典型的 reward hacking。
2. **推进项与已有势能重复**：`Φ` 里的 `1.5 × 球到门距离` 本身就是单调的推进激励；
   再加一个线性位置项属于重复激励，且是非势能项（会改最优策略），净效果是扰动。
3. **过程奖励 vs 结果奖励**：三项奖励的都是过程，在 30 s 短幕 + 弱脚本对手下，
   策略守过程分比冒险射门更划算；死球数从 9.3 涨到 11~12.7（开始把球往边线带）。

想用的话：先按旧奖励把抢球射门训稳；要更强进攻就抬 `shaping_ball`（1.5→2.0~2.5，
势能项安全）；要做协作/干扰用半场门控 + 0.004 级权重，并把预算提到 500 万步以上再判断；
**评估别只看进球**，同时看控球率、干扰距、死球数（本轮正是靠这三个指标发现"控球率涨了但球往后跑"）。

### 18.11 短程传球：物理上不成立（实测）

用仿真本身的物理测：狗以动作饱和速度 **0.45 m/s** 正面顶球。

| 恢复系数 e | 摩擦 a | 出脚球速 | 滚到静止 |
|---|---|---|---|
| 0.3 | 0.8（典型） | 0.54 m/s | 0.22 m |
| 0.5 | 0.8 | 0.63 m/s | 0.28 m |
| 0.7 | 0.8 | 0.72 m/s | 0.36 m |
| 0.7 | 0.3（最理想） | 0.75 m/s | 0.96 m |

球要滚 d 米需要出脚速度 `sqrt(2·a·d)`：0.6 m 就要 0.98 m/s（a=0.8），
**比顶球能给的上限 0.75 m/s 还高**。所以现在的"传球"实际只有 0.3~0.4 m，
等于没有传球——这也解释了为什么学出来的都是贴脚带球。

要让短传成立，最小改动是加 **kick 通道**（真机 `push` 模式 1.5 m/s × 450 ms 已具备，
球出脚约 2.2 m/s、滚距 3 m）：

- 训练侧：动作 +1 维（触发 kick）、观测 +1 维（kick 冷却/可用），
  奖励加"接球成功"（球被队友首次触碰且位移 > 0.5 m）；
- 精度：站位横向误差 5 cm → 出脚方向偏 10° → 1 m 处偏 0.18 m、2 m 处 0.36 m，
  接球圈 0.43 m，所以 **2 m 以内可行**，再远就要更准的站位；
- 代价：扩动作空间就要重训，且真机要走 push 脉冲链路，属结构性改动。

诊断工具：`python -m train.passing`（上面两张表都是它输出的）。

### 18.12 提速与"高速短冲推球"（2026-11-16）

两件事分开看：**档位**（整场能跑多快）和**短冲**（450 ms 的一脚爆发）。

#### 部署端怎么用

#### 短冲的实现（两侧同一套规则）

真机上直接对标 §17 的 push 模式（`vel_des` 1.5 m/s × 450 ms、步高不变、无腿部动作），
所以落地不需要新链路。触发条件三条同时满足：

1. 前进指令 `a[0] ≥ 0.80`（策略"想全速往前"）；
2. 球在机身前方 ±0.50 rad（28.6°）内且距离 ≤ 0.90 m；
3. 冷却 1.2 s 已过、且冲刺位移不会把自己推出场地；
4. 若 `rl_dash_goal_cone > 0`，还要求冲刺方向与"球→对方门"方向夹角 ≤ 该值（0.9≈52°）。

#### 实测结论（细节见 `train/README.md` §14）

| 项 | 数字 |
|---|---|
| 物理收益 | 0.45→0.90：顶球出脚 0.64→1.31 m/s、滚距 0.32→1.30 m、跨半场 11.1→5.6 s |
| 短冲收益 | 任何档位都给 2.2 m/s 出脚、3.5 m 滚距（= 射门力度） |
| 纯提速（同分配、5 种子） | 球推进 1.85→0.66~0.69，死球 7.3→17.8~25.7，进球不升 |
| 短冲（无门控） | 进球 4.90→6.60，死球 11.1→36.3（其中 88%~95% 是自伤） |
| 短冲（门控 52°） | 进球 5.00、死球 23.5（压 35%，但也就回到基线水平） |
| 对手也 0.90 m/s | 进球 5.00 vs 基线 4.83，但开始丢球 1.17 → **速度优势在对手同样快时消失** |

因此本轮的上机建议：

1. **仍然用 0.45 档权重比赛**，它是唯一有"5 球/半场"证据的策略；
2. 要试短冲：只开 `rl_dash:=true -p rl_dash_goal_cone:=0.9`，并把
   `rl_speed_limit` 压到 0.20~0.30 先看 450 ms 那一脚会不会把球送进死区
   （死区判定见 §13，距围挡 0.8 m 就停）；
3. 要真正提速：先给奖励加"球到最近死区的距离"势能项，再 500 万步 + `--peer-opponents`
   换同样快的权重对练，否则是在打 0.30 m/s 的假对手；
4. 别用 `train/matchup.py` 的比分当判据（1 队镜像缺陷，自对自就能 26:0）。

#### 18.12.1 "我们比对手快"值多少（`python -m train.race`）

| 档 m/s | 3 m 球耗时 | 相对 0.45 | 能容忍的距离劣势 |
|---|---|---|---|
| 0.45 | 5.90 s | 1.00× | 1.00× |
| 0.90 | 3.05 | 1.93× | 1.67× |
| 1.48 | 1.90 | 3.11× | 2.60× |

- 救球（侧前方 1.5 m、等距起步）：0.90 档快 1.95 s，1.48 档快 2.75 s；
- 但散球时间只占半场 **35.4%**（约 85 s / 4 min），其余时间是"有人在控球"，比的是控球质量；
- 胜负线：3 m 球下 0.90 档对 0.68 领先 0.95 s、对 0.90 打平、对 1.22 落后 0.75 s。

一句话：**提速的收益取决于对手速度**。对手 ≤0.4 m/s 时 0.45 已经稳赢争抢，提速是纯成本；
对手在 0.6~0.9 时提速才有意义，但必须先解决"触球后自己把球推进死区"（§18.12 表）。
短冲（0.9 m 内触发）是射门手段，不能当远征冲刺用。

#### 18.13 仿真保真度：现在这套训练能替代真机吗

分三层看：**契约层**（观测定标、动作缩放、规则判定）实测 max|Δ|=0，可信；
**决策层**（奖励形状、信息价值、角色分工）只在仿真内部的相对比较里成立；
**执行层**（动力学/接触/时序）是纯运动学，有 3 条可量化偏差：

1. 球出脚速度高估 ~1.5×：仿真按弹性碰撞 (1+e)·v_dog，实机是持续接触推球（≈v_dog）；
2. 转向响应偏快：仿真 τ_w=0.10~0.30 s，部署端却给 `turn_response_grace=1.0`；
3. 起步没建模：仿真 50~150 ms 就动，实机要先起振步态（`--push` 也是先走 250 ms）。

未建模的还有：腿部/步高/打滑/摔倒/过热/电量/球旋转/围挡反弹/狗的矩形身体/缠腿/
动捕成段断流/裁判暂停。

因此：**观测与奖励层面的结论可以信，绝对战绩与"几秒到球"不能信**。
标定工具已就绪：

```bash
python -m train.calibrate --self-test          # 拟合器自检（2 帧/0.15s/0.95 全中）
ros2 run pkg_soccer record_motion --ros-args -p output:=/abs/path/id.csv
python -m train.calibrate /abs/path/id.csv     # 输出应写回 EnvConfig 的 latency/tau/tau_w
```

顺序：标定 → 重训 → 影子模式 → 0.2 限速上机（详见 `train/README.md` §15）。

## 19. 比赛主程序改造：参数精简 + 出界/进球后自动继续（2026-11-17）

> 本节**覆盖**前文与默认值有关的内容（§3/§11/§17 里的 `enable_motion:=true`、`use_mocap_goals`、
> `max_run_time=120`、`max_kicks=8`、进球即终态等描述已过时）。

### 19.1 只需要 6 个参数

```bash
ros2 run pkg_soccer soccer --ros-args \
  -p dog_name:=<本狗运动接口命名空间> \
  -p dog_pose_topic:=/vrpn/dog1/pose \
  -p teammate_pose_topic:=/vrpn/dog2/pose \
  -p opponent1_pose_topic:=/vrpn/opp1/pose \
  -p opponent2_pose_topic:=/vrpn/opp2/pose \
  -p attack_goal:=goal_right
```

- **1v1**：去掉 `teammate_pose_topic` / `opponent2_pose_topic`。
- **单狗**：`-p rl_policy:=stage2`（23 维）或 `-p control_mode:=rules`。
- **只观察不动**：`-p enable_motion:=false`。
- **换边**：把 `attack_goal` 换成 `goal_left` 重启（它是只读启动参数）。

新的默认值：`control_mode=rl`、`rl_policy=attacker`、`enable_motion=true`、
`use_mocap_goals=false`、`field_length=10`、`field_width=5.5`、`goal_width=1.5`、
`goal_line_inset=0.415`、`max_run_time=600`、`max_kicks=200`。

### 19.2 场地与球门不再依赖门刚体

`use_mocap_goals=false`（新默认）时由 `soccer.py::static_field` 按尺寸算：
门线 x=±4.585、门宽 1.5、场地 ±5 / ±2.75、`goal_yaw=0`（右）或 `π`（左）。
好处：少两个话题、少一次标定，也不会因为门刚体断流停摆。
需要门刚体时加 `-p use_mocap_goals:=true`（原 §14 的标定流程仍然可用）。

### 19.3 比赛循环：只有"真正的故障"才结束

| 事件 | 旧行为 | 新行为 |
|---|---|---|
| 进球 | `GOAL` 终态，永不恢复 | 记 1 分 → `WAIT_PLAY` 暂停等裁判 |
| 球出界 / 停在门线后 | `stop()` 终态 | `WAIT_PLAY` 暂停等裁判 |
| 球进死区 / 双方僵持 8 s | `WAIT_REFEREE` + 要求球移动到"指定点" | `WAIT_PLAY`，任意发球点都算 |
| 恢复条件 | 需重启程序 | 球回到**任一发球点**、静止 0.4 s、狗也静止 → `rearm()` 自动继续 |
| 姿态故障 / 狗离场 / 超时 | `stop()` | 不变（仍是终态） |

发球点固定为 3×3 网格（`service_point_x=2.5`、`service_point_y=1.25`，含开球点），
**与训练端 `train/obs.py::SERVICE_POINTS` 逐点相同**（`train.verify --match` 会断言这一点），
容差 `service_point_tolerance=0.40 m`。
**赛前请用卷尺核对十字标记的实际位置**，若与这两个值差得远，直接改它们：
`-p service_point_x:=2.5 -p service_point_y:=1.25`（或放宽 `service_point_tolerance:=0.5`）。
另有兜底：暂停超过 `resume_timeout=25 s` 且球已静止在场内时也会放行。

`rearm()` 会清零射门计数、重新计时（暂停时间不计入 `max_run_time`），
RL 端还会清空上一动作/接触/短冲/僵持状态。

### 19.4 2v2 与 1v1

- 话题：`teammate` / `opponent1` / `opponent2`，旧的 `opponent_pose_topic` 仍兼容。
- 观测维度由**权重**决定：41 维才有队友（29-34）和次近对手（35-40）槽位；
  29 维只有最近对手。配置了队友但权重是 29 维时启动会打 warning。
- 自动选权重：41 维权重命名 `policy_team_<role>_actor.npz` 放在 `pkg_soccer/` 下会自动优先加载，
  否则用 `policy_duel_<role>_actor.npz`（当前是 29 维），也可 `-p rl_model_path:=<npz>`。
- 升级到 2v2 的权重来源：`runs/*/policy.npz` 里有 21 份 41 维 attacker 权重，可直接拷过去
  （拷前先用 `python -m train.eval_match` 之类的方法挑一份，别盲选）。

### 19.5 自检

```bash
python -m train.verify --match      # 比赛循环：进球/出界 → 暂停 → 发球点 → 继续（含 RL）
python -m train.verify              # 全量：观测契约 / 前向 / 速度档 / 比赛循环 / 环境
```

`--match` 覆盖：发球点网格、进球计分、出界暂停、门线后未进球、任意发球点恢复、
RL 端在对手断流时也能恢复，以及 `max_run_time ≥ 480`、`max_kicks ≥ 50` 的护栏。

### 19.6 取消 leg / gait 踢球，改为"提速推球"（2026-11-17）

结论：**不切位控、不抬腿、不用 305 摆动腿相位**，只靠速度把球撞出去。
`soccer.py` 里 `kick_mode`、`kick_dry_run`(leg/gait 部分)、`kick_runner`、`gait_runner`、
`poll_leg_kick`、`send_kick_recover`、`last_contact` 全部删除，`kick_mode` 参数也不存在了；
`leg_kick.py` / `gait_kick.py` 不再被主程序 import（可整文件删掉，独立脚本仍可用）。

**速度相关的默认值（Config）：**

| 参数 | 旧 | 新 | 作用 |
|---|---|---|---|
| `approach_speed` | 0.45 | **0.70** m/s | 绕球/走位速度 |
| `kick_speed` | 0.55 | **0.90** m/s | 触球前的推进速度 |
| `kick_max_speed` | 1.5 | 1.5 m/s | 推球脉冲（协议 vel_des 上限，不能再高） |
| `kick_max_ms` | 450 | 450 ms | 脉冲时长（1.5×0.45 ≈ 0.68 m 冲程） |
| `walk_step_height` | 0.05 | 0.05 m | 305 步高，跑更快可试 0.06 |

校验上限也放宽：`approach_speed ≤ 1.0`、`kick_speed ≤ 1.2`（构造时检查）。

**脉冲与 KICK 的关系（重要，别再改回去）：**
KICK 会因为"球已移动 0.15 m / 已冲出 `kick_travel=0.2 m`"提前结束，所以脉冲**不能**绑在
`state == 'KICK'` 上，否则推球会被截成 0.1~0.2 s。现在的规则是：
进入 KICK 触发一次脉冲 → 脉冲跑满 `kick_max_ms`；只有
`paused`（进球/出界等暂停）、`WAIT_POSE`（动流断流）、`WAIT_REFEREE`、终态才立刻掐断。

**RL 模式的速度不在这里**：连续策略的速度 = 权重里的 `action_scale`（0.45 或 0.90 档），
`rl_speed_limit` 只能往下压不能往上抬。想更快就换 0.90 档权重，或开 `-p rl_dash:=true`
（1.5 m/s × 450 ms 的冲刺，规则与训练端 `TeamEnv._dash_commands` 一致）。

**回退办法**：`-p approach_speed:=0.5 -p kick_speed:=0.6` 就能退回原来的一档；
`-p kick_max_speed:=1.0 -p kick_max_ms:=300` 是温和推球。

| `sp_e`（当前部署） | 300k，0.90 档 + 门控短冲 | 9.0 | 1.0 | **0** | **+8.0** | 90.7 |
| `sp_h` | 再训 500 万步，对手=自己 | 2.0 | 1.0 | 0 | +1.0 | 47.7 |
| `sp_i` | 300 万步，对手=脚本 0.60 | 12.3 | 5.7 | 4.5 | +6.6 | 100.0 |
| `sp_j` | 300 万步，队友=自己、对手 `sp_e` | 11.7 | 7.7 | 3.5 | +4.0 | 86.3 |

两种退化模式，都会在真机上放大：

- **抱球退化**（`sp_h`）：控球率 45%→66%、贴球 1.05 m，但球均 x 从 +1.83 掉到 +1.46、
  进球 6→2.5。自博弈里"控住不丢"比"冒险推进"划算。
- **乌龙**（`sp_i`/`sp_j`）：失球 100% 是"我方最后触球后球进自家门"。面对 0.60 m/s 的对手
  正面对抗抢不过，长训收敛到**侧向捅球**，而侧向捅球不控制出球方向。

`sp_e` 没有这两个毛病，不是因为它更强，而是**它只训了 30 万步，还没学会这些坏习惯**。

### 19.9 方向感：短冲门控默认改成 52° 锥（2026-11-17 晚）

`rl_dash_goal_cone` 的默认值从 **0.0 改成 0.9 rad（约 52°）**：短冲只在"朝对方球门"
的方向锥内触发，其余方向一律不发 1.5 m/s 脉冲。

理由（实测，`train/README.md` §17）：`sp_e` 在被推的球里**有 40% 是朝自家门方向**，
而短冲是全局最快的动作（1.5 m/s × 450 ms）。不开门控时它会把这种乱推放大成乌龙。

```bash
# 现在的等价写法（默认已是 0.9，写出来只是明确）
-p rl_dash_goal_cone:=0.9
# 想让冲门更严格（40°）
-p rl_dash_goal_cone:=0.7
# 回到旧行为（不推荐：这是朝边线/乌龙的主要来源）
-p rl_dash_goal_cone:=0.0
```

另外记录一条**仿真口径**的事，别和真机混淆：

- `--ball-restitution` / `--ball-drag` 只影响**训练与仿真评估**，真机上球怎么滚由物理世界决定；
- 但这两个参数决定了策略学到什么：默认的 e=0.3~0.7 会把球弹飞（出脚速度 1.3~1.7 倍狗速），
  狗无法控制方向；改成 e=0.15 / drag=1.2 后，同一份 `sp_e` 的"朝门角"从 78° 降到 64°、
  朝己方门从 40% 降到 24%、进球 5.0 → 7.5。
- 所以**真机标定球物理（§15.4）比继续调奖励更值得做**：那才是"方向感"的地基。
